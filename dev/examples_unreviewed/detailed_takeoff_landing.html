2DOF Detailed Takeoff and Landing#

Here we discuss how to optimize the takeoff and landing sequences for aircraft using the two-degrees-of-freedom (2DOF) equations of motion. When we say “detailed takeoff and landing,” this simply means that we model the aircraft trajectory in more detail than other simplified mission representations. This means two main things:

  • We model the takeoff portion of flight using a series of phases, such as ground roll, rotation, and multiple climb phases. Similarly, we model the landing portion of flight using a series of phases, such as approach, flare, and touchdown.

  • Instead of using the energy-state approximation for the aircraft equations of motion, we use the full two-degrees-of-freedom (2DOF) equations of motion. This means that there is a notion of angle of attack and aircraft pitch within the flight dynamics equations. These mission methods are both detailed in the Mission Analysis doc page.

These considerations allow us to model specific parts of the aircraft trajectory in more detail, which is especially useful for certain performance-based disciplinary analyses, such as acoustics and controls.

Defining the trajectories#

Our objective for this example is to model the takeoff and landing trajectories of an aircraft for acoustic modelling. Current noise regulations specify where acoustic measurements must be taken, and our trajectory phases will start and end at those points to ensure we can pass aircraft performance data such as altitude, throttle, speed and distance to our acoustic modelling tool.

We use phase_info dictionaries (as normal) to define the phases of takeoff and landing. A general description of these dictionaries can be found in the mission_definition docs. For these examples we will model takeoff and landing as separate standalone missions, and will not include the full flight to a destination. This reduces the size of the optimization problem, and is all that is required for our acoustic use case, however these examples could be linked into a comprehensive mission analysis with climb, cruise and descent phases if required.

The default phase_info dictionaries for takeoff and landing can be found in aviary/models/missions/.

Defining the takeoff trajectory#

We follow the diagram below to model the takeoff trajectory with the following phases:

  • Groundroll (A->B)

  • Rotation and liftoff (B)

  • Initial climb to obstacle clearance (B->C)

  • Climbout (C->D)

  • Engine Cutback (D->E)

  • Continuous climb (E->F)

P1 and P2 correspond to microphone locations for acoustic certification.

  • P2 is at 985 ft (300 m) altitude

  • P1 is at a distance of 21325 ft (6.5 km) from start of groundroll

We will split phases C->D and E->F with C->P2, P2->D, and E->P1 and P1->E so that we do not have to interpolate the trajectory to get the necessary data for the acoustic measurements.

You will notice that this phase_info is a little more complex than the standard two_dof or energy_state default phase_infos, and you might’ve seen the units of ‘time’ are ‘incorrect’ and inconsistent between phase AB and the others! This is correct but confusing and explained below:

Note

The energy-state and 2DOF equations of motion (EOM) use ‘time’ as the integration variable, which is the default in Dymos. It was found that reformulating the 2DOF EOM using a different integration variable resulted in more stable convergence of takeoff and landing trajectories. These reformulated EOM are called ‘solved_2DOF’, and these are used in this example.

There is a specific groundroll EOM used for that phase as a special case as there are fewer degrees of freedom.

Note

The integration variable for the groundroll phase (AB) is reformulated to be velocity. Dymos always calls the integration variable ‘time’, which results in the phase_info needing to set ‘time’ options with velocity units of ‘kn’. The integration variable for the other solved_2DOF phases is distance, so all the other phases have ‘time’ options with distance units of ‘ft’.

Overview of intention of user_options for each phase:#

  • AB - Groundroll: We set the initial conditions of 0 distance, time and velocity and mass equal to the gross mass. Integration variable is velocity with wide bounds.

  • Rotate: Initial rotation will be between 1000-3000ft after start of groundroll and will complete within 200-2000ft (time initial and duration bounds), we allow optimizer to control mach linearly within the phase between 0.18 and 0.2. Altitude is fixed at 0 ft. We add a constraint that at the end of the phase the normal_force = 0 (i.e. we are about to lift off).

  • BC - Climbout to obstacle: B is between 1000-16000ft duration is 500-1500ft. We allow optimizer to optimize both mach and altitude with linear variation through phase. Phase ends at altitude of 50ft (C), which is the FAA obstacle clearance altitude.

  • C-P2 - Climb to acoustic measurement: Optimize mach and altitude linearly. Final altitude is 985 ft.

  • P2-D - Climb to cutback: Optimize mach and altitude linearly

  • DE - Cutback: Short ‘duration’ (distance) bounds. Optimize mach and altitude with polynomial order of 2. Add constraint on flight path angle of 2.29 degrees which corresponds to a 4% slope as per FAA regulations.

  • E-P1: 4% climb to acoustic measurement. Optimise mach and altitude linearly within bounds. Maintain flight path angle constraint. Add additional constraint to distance to ensure P1 is at 21325 ft (6.5km) from start.

  • P1-F: Maintain 4% climb, optimize mach and altitude linearly out to arbitrary 30000ft from start.

General notes on the phase_info#

All of the phases contain initial guesses, which are important to help the optimizer converge well, and are much more important for the 2DOF model than the energy-state model.

We generally use polynomial controls of order 1 to simplify the optimization problem. This means that the control variables (Mach and altitude) are linear within each phase. You can increase the order of the polynomial controls by setting altitude_polynomial_order or mach_polynomial_order to a higher value. You can also set them to None to have the optimizer control the values at every node.

We add any constraints needed for the trajectory in the constraints argument passed inside of user_options. Any arbitrary variable present in the phase ODE can be constrained. You can use boundary or path constraints by setting the type argument in the constraint dict (for example throttle)

We optimize mach and altitude using the mach_optimize and altitude_optimize flags. You can choose to disable optimization of these variables by setting them to False for any phase. Aviary internally handles the connections for Mach and altitude between the phases to ensure continuity in the trajectory.

The objective function used for this example is to minimize ‘time’, since this is inbuilt into Aviary and simple. If the acoustic measurement tool was in the loop a better custom objective might be to minimize noise at the measurement points subject to performance constraints to ensure the aircraft was being operated ‘safely’ (e.g. minimum speeds).
